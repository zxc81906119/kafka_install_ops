# 2026-11-11 CBOM（PQC 盤點）＋Jenkins＋OPA：設計討論

背景：客戶要 Confluent Platform 提供 CBOM 以利 PQC 盤點。使用者要 Jenkins 自動化產生 CBOM、用 OPA 判斷規則、產出密碼學資產合規報告；先討論定案再實作。使用者明確說不要參照機器上既有的 cbomlab 容器。

## 已定案（使用者 11-11 選擇）
- 盤點四層都做：①憑證、金鑰檔 ②JDK／OS 密碼設定（cbomkit-theia：certificates、javasecurity、opensslconf、secrets）③平台設定（Kafka properties 的 TLS、SCRAM、Secret Protection；沒有現成工具，自寫收集器轉 CycloneDX）④實際連線的 TLS 掃描；另加原廠 jar 的密碼函式庫（SBOM），並向 Confluent 要原廠 SBOM／CBOM。
- OPA：pipeline 裡直接 `opa eval`（不架常駐服務、不架 CBOMkit）。
- 規則基準：NIST IR 8547＋FIPS 203／204／205；客戶有指定再加。
- 交付：手冊新增一章（三步驟：lab 手動 → 手冊 → 腳本）；Jenkins 在 lab 用容器模擬。
- 格式：CycloneDX CBOM（ECMA-424；工具多輸出 1.6，先用 1.6）。

## 查到的事實（來源：cyclonedx.org、github.com/cbomkit、confluent.io）
- CP 沒有原始碼，sonar-cryptography（掃原始碼）用不上；cbomkit-theia 掃目錄／映像，Apache-2.0，沒有正式 release 版本號（離線引進要固定 commit／digest）。
- CBOMkit 官方支援 OPA 外掛判斷（`quantum_safe.rego`，findings：bom-ref、result、rule），可當規則寫法的參考。
- Confluent 只公布 Confluent Cloud 的 PQC 路線圖，沒找到 CP 的 CBOM／PQC 聲明。
- 預期結果：現況（RSA／ECDSA 憑證、ECDHE）在 PQC 規則下都是 quantum-vulnerable；報告的價值是盤點與遷移優先序。

- **JFR（lab 實測）**：kb01 用 `sudo -u cp-kafka jcmd <pid> JFR.start name=cbom maxsize=50m jdk.TLSHandshake#enabled=true jdk.X509Certificate#enabled=true jdk.X509Validation#enabled=true jdk.SecurityProviderService#enabled=true …`，不用重啟。134 秒：SecurityProviderService 2,007 筆（28 種「類型｜演算法｜provider」，含 `KEM｜X25519MLKEM768` 8 次、`ML-KEM` 8 次、HKDF-SHA384、AES/GCM、RSASSA-PSS、XDH）、TLSHandshake 21 筆（peerHost、peerPort、protocolVersion、cipherSuite、certificateId；沒有 named group）、X509Certificate 18 筆（subject、algorithm、keyType、keyLength、validUntil）；有 stackTrace（追得到 org.apache.kafka／io.confluent 的呼叫點）。.jfr 4.3 MB，`jfr print --json` 後 12.8 MB。待查：openssl `-tls1_2` 的 3 次連線沒有看到 TLSv1.2 的交握紀錄。
